# ADR 0048 — On external images, /venv/main is a per-file symlink mirror of the engine's own site-packages

- **Status:** Proposed
- **Date:** 2026-09-28
- **Decision owner:** Rob Ballantyne
- Supersedes: the `--system-site-packages` design of `/venv/main` in
  `tools/convert-non-vast-image.sh` (added with #76; recorded only in its comments:
  "Uses the system Python directly — no conda Python, no library conflicts")
- Related: ADR 0001 (static checks are the fast gate, the build + smoke test is the
  correctness check), ADR 0005 (live-GPU QA gate), ADR 0044 (vllm-omni serverless);
  [docs/invariants.md](../invariants.md)

## Context

External images (vllm, vllm-omni, openwebui, sglang, ollama, and every image the imagegen
`external` template generates) are an upstream image converted by
`tools/convert-non-vast-image.sh`. The upstream installs its engine and torch stack into
its own interpreter's site-packages. The convert script then creates `/venv/main` with
`uv venv --relocatable --seed --system-site-packages`, so the venv can import the engine
without a copy, stays small, and syncs to `$WORKSPACE` through
`ROOT/etc/vast_boot.d/37-sync-environment.sh`. On vllm and vllm-omni the engine then runs
*through* `/venv/main` (the `vllm` shebang is rewritten to `/venv/main/bin/python`), and
openwebui's supervisor script activates it.

uv does not count packages a venv inherits through `include-system-site-packages` as
installed. It discovers installed distributions only in the environment's own install
scheme, not on the interpreter's `sys.path`. This is a known upstream gap: astral-sh/uv
issue #4466 (open since 2024), with two unmerged fixes (#9849, a draft stalled since April
2025; #11670, a maintainer's implementation of exactly the semantics needed here, closed
by its author in June 2026). So every `uv pip install` into `/venv/main` — ours or a
user's, and uv is the tool the image teaches — re-resolves as if the engine stack were
absent.

Measured 2026-09-28, local docker on the current tags plus one live instance:

- vllm v0.30.0, vllm-omni v0.28.0 and v0.30.0: torch 2.13.0+cu130 lives only in the system
  site-packages; `uv pip install --dry-run --python /venv/main/bin/python "torch>=2.0"`
  plans torch 2.14.0. openwebui v0.11.4: torch 2.9.1+cu128, same plan.
- Live failure: a template setting `PROVISIONING_PIP=voxcpm==2.0.3` on vllm-omni installed
  136 packages into `/venv/main`, torch 2.14.0 and torchaudio 2.11.0 among them; the engine
  imported that torch next to the system torchvision and died with
  `RuntimeError: operator torchvision::nms does not exist`. voxcpm needs only `torch>=2.5`,
  and every release tried (2.0.3, 2.0.0, 1.5.0, 1.0.5) resolves the same way — the version
  is not the cause, the install target is.
- It has already happened at build time: vllm v0.30.0's `/venv/main` owns 32 copies of
  system packages, three at different versions (numpy 2.3.5 over the engine's 2.2.6,
  mistral_common 1.12.0 over 1.11.7, six 1.17.0 over 1.16.0), and the engine runs the venv
  copies. They are the dependency closure of our own two build-time uv installs (ipykernel
  in the convert script; the vLLM audio extras). pip, which does count inherited packages,
  installs 4 packages for the audio extras where uv installs 28.
- Interpreter detection is a heuristic: the first `python3` on `PATH` other than
  `/opt/sys-venv`. It is right on vllm, vllm-omni and openwebui by PATH order, and wrong on
  sglang: it finds the engine's `/opt/sglang/bin/python3`, uv resolves that venv
  interpreter to its base, and `/venv/main` inherits `/usr/bin` — so it has never seen
  sglang's packages, and nothing installed there reaches the engine, which runs
  `#!/opt/sglang/bin/python3`.
- Not exposed: the base and pytorch images, whose `/venv/main` is a conda env that owns its
  packages (the same dry run makes no changes); ollama, which has no Python engine.

## Options considered

1. **Install into inheriting venvs with pip instead of uv** (auto-selected from
   `pyvenv.cfg`), optionally with a venv-scoped `pip.conf` pinning the torch stack.
   pip counts inherited packages, and on vllm-omni `pip install voxcpm==2.0.3` kept the
   engine's torch. Rejected: it fixes only the installs we run. A user typing
   `uv pip install` — the default the image teaches — is left exactly where the live
   failure happened. pip also enforces metadata pins the upstream deliberately violates
   (torch 2.13 pins `nvidia-nccl-cu13==2.29.7`; the image ships 2.30.7), so it downgrades
   NCCL into the venv whenever torch is in a resolution.
2. **uv with a constraints file generated from the inherited set.** Rejected: local-version
   wheels (`torch==2.13.0+cu130`) are not on the index, so it fails with no solution;
   stripping the suffix makes uv download a second copy of the same torch, because it
   still does not count the inherited one.
3. **Install into the system interpreter (`--system`), or make `/venv/main` the system
   interpreter itself.** The latter was measured and resolves correctly (uv reports
   "Using Python ... environment at: /usr"). Rejected: installs would no longer live in a
   directory with `pyvenv.cfg` or `conda-meta`, so stage 37 would stop syncing them — it
   breaks the `$WORKSPACE` persistence contract.
4. **A uv wrapper on PATH.** Rejected: it cannot make uv see inherited packages, only
   redirect to pip or refuse, and it misses `python -m uv` and absolute paths.
5. **Patch uv (carry #11670).** Measured: built from the branch, it fixes the case on the
   unchanged image (plain `uv pip install voxcpm==2.0.3` in an activated `/venv/main`: no
   torch reinstall, 63 packages landing as real venv files, engine imports). Rejected: the
   branch sits on uv 0.11.20 and lacks the `cu132` torch backend our pytorch builds use;
   rebasing onto 0.12.19 conflicts in 14 files on its first commit; and a fork couples our
   CUDA support to our rebase speed against a twice-weekly uv release cadence, for a design
   its author abandoned without a stated reason.
6. **Symlink the venv's whole site-packages directory to the engine's.** Rejected: uv
   resolves the link when placing entry-point scripts and aborted a real install halfway
   ("failed to query metadata of file /venv/main/bin/voxcpm").
7. **Directory-level symlinks** (one link per top-level package, 524 on vllm). Rejected on
   evidence: uv installs and uninstalls per file path, so upgrading dill wrote the new
   files THROUGH the directory link into the system tree — 0.3.8 code beside 0.4.1
   metadata in the engine's own site-packages — and it did not recognise some linked
   packages at all.
8. **Link only the `.dist-info` metadata.** Rejected: uv still reinstalled torch and the
   engine broke with the same `torchvision::nms` error.
9. **Copy the engine stack into `/venv/main`.** Correct in principle — it is what the
   pytorch image does — but it duplicates 17 GB into a new layer on vllm and syncs all of
   it to `$WORKSPACE`.

## Decision

On an external image, `/venv/main` is a fresh venv on the engine interpreter's base Python,
with `include-system-site-packages = false`, whose site-packages is a **per-file symlink
mirror** of the directories the engine interpreter itself imports from: every directory is a
real directory, every file is a symlink to the engine's file. uv and pip then see the whole
engine stack as installed in `/venv/main`, and every install, upgrade and uninstall — ours
or a user's, uv or pip — resolves against it and lands as real files in the venv, which
syncs as before.

Measured in the published images by replaying the new convert steps: on vllm v0.30.0 the
mirror is about 154k links, built in about 5 s, and `venv-mirror verify --build` takes about
12 s, most of it importing vllm (on CI runners, about 21 s and 20-25 s). After our own
installs the venv owns only what they genuinely add; a real `uv pip install voxcpm==2.0.3`
keeps the engine's torch and leaves the engine's files byte-identical; `--reinstall`, `-U`,
uv and pip uninstall, and a colliding file from another distribution each replace or remove
the link, in every uv link mode, and never write through it.

## Binding conditions

1. **The engine interpreter is declared, never guessed.** Each external Dockerfile, and the
   imagegen external template, declares the engine's interpreter and the module that proves
   it (`VAST_ENGINE_PYTHON`, `VAST_ENGINE_IMPORT`; `none` for an image without a Python
   engine). The build fails if the declaration is missing, if the interpreter's base Python
   does not match the one `/venv/main` is created on (path and major.minor), or if the
   engine module does not import through `/venv/main/bin/python` from under the mirror.
2. **The mirror reproduces exactly what the engine interpreter imports from** — the site
   directories on its own `sys.path`, in order, first one wins (not
   `site.getsitepackages()`, which for a venv engine that inherits lists only the venv). On vllm that includes
   `/usr/lib/python3/dist-packages`, which is on today's path; on sglang it is only
   `/opt/sglang`'s site-packages, which is all the engine sees.
3. **No directory under the venv's site-packages is ever a symlink.** A directory link lets
   uv write into the engine's tree (option 7). This is the linter invariant, and the
   runtime check asserts it too.
4. **One placement rule, on a fresh venv.** The build refuses a venv that already holds
   anything, and the first source providing a project wins. A file NO mirrored project
   lists (`__pycache__`, Debian's metadata-less trees) goes only into a directory created
   for the same source; otherwise Debian's orphan `pkg_resources/` filled the one made for
   `/usr/local`'s setuptools, and uninstalling setuptools left an importable empty package.
   A file a project lists may share a directory another source created: right for a
   namespace package (`nvidia/`), and, for a regular package, a lower source's file becomes
   importable where the engine would not see it (no supported image has such a pair). A
   source may describe one tree twice (Debian ships both `cryptography-41.0.7.dist-info`
   and `cryptography.egg-info`): the dist-info is chosen, the other entry's metadata is
   left out, its code is not. Debian metadata without a `RECORD` gets one only when it can
   be complete and the project's alone (its `top_level.txt` trees, or its own name when
   there is none, and nothing another mirrored project lists); otherwise it keeps none and
   pip refuses to uninstall it, as it always did. A partial RECORD was worse: pip reported
   a clean uninstall of blinker while `import blinker` still worked, and `lazr.uri`'s took
   `lazr.restfulclient`'s files with it. A manifest (`.vast-venv-mirror.json`) records the
   sources and each mirrored project's version.
5. **The mirror is built, and all our installs target `/venv/main`, before the image is
   finished.** The convert script builds the mirror on a fresh venv BEFORE any install into
   it, so our installs (ipykernel, the vLLM audio extras, vllm's `ray[default]`, which used
   to run `--system` after convert) resolve against it and create no shadows; `ray.sh`
   activates `/venv/main` so the dashboard runs where its extras are. The venv is created
   without `--seed`: on python < 3.12 the seed puts setuptools in the venv, where it beat the
   engine's (on openwebui, setuptools 84, which has no `pkg_resources`). `venv-mirror verify
   --build` runs in the same RUN as `env-hash > /.env_hash`. It checks: inheritance off, no
   directory links, no dangling links, one installed copy per project, no mirrored project
   replaced during the build (the manifest's versions against what the venv now owns),
   each declared engine module importing through the venv from files outside it, and uv
   planning no reinstall of torch or the engine's project. uv re-checks an explicitly
   requested package's own pins, and an upstream can ship a stack that breaks them, so
   changes to other packages in that plan are reported, not failed. The instance test
   runs the same checks except the build-time one: after first boot a user may replace
   anything.
6. **After first boot, `/venv/main` is the user's.** No boot stage modifies it. The mirror is
   never refreshed, pruned or re-linked on an instance: a user's uninstall stays
   uninstalled, a downgrade stays downgraded, and co-located instances sharing a
   `$WORKSPACE` volume cannot race each other over it. Any boot-time or instance-test check
   only reads. A new image is a new mirror: `env-hash` already gives every change in package
   versions its own `.environment_sync` directory.
7. **sglang runs through `/venv/main`.** The mirror writes venv-local console scripts (shebang
   `/venv/main/bin/python`) for the engine's entry points, without overwriting an existing
   file, so `sglang serve` from an activated shell or `sglang.sh` uses the venv and
   installs there reach the engine. `/opt/sglang` stays untouched. This changes how the
   engine starts and must pass the sglang QA cell, including a live serve.
8. **Proven on a feature-branch build of vllm, with a live serve**, before the convert
   script change reaches any other image.

## Consequences

- A user's `uv pip install` on an external image can no longer install a second torch
  under a running engine. The worst case becomes an explicit request (`uv pip install
  torch==<other>`) doing what it says, as on the pytorch image.
- The 32 build-time shadow copies on vllm disappear on the next build. That changes what
  the engine runs (numpy 2.3.5 back to the engine's own 2.2.6, and so on), so each image's
  first mirror build goes through its QA cell as a behaviour change, not a no-op.
- sglang's `/venv/main` grows from about 17 base-Python packages to the engine's whole
  stack, and its engine can be extended from the venv for the first time. `/venv/main` on
  sglang no longer sees `/usr/lib/python3/dist-packages`, which the engine never saw either.
- That extensibility cuts both ways on sglang. Its upstream stack breaks torch's own pin
  (torch pins `nvidia-nccl-cu13==2.29.7`, the image carries 2.30.7), and uv "repairs" it on
  any install that touches torch: `uv pip install voxcpm==2.0.3` in the venv also plans
  NCCL 2.29.7, exactly as it does against sglang's own `/opt/sglang`. Before this change a
  user's install never reached the sglang engine; now it does, NCCL included, which
  matters for multi-GPU serving. vllm's stack does not trigger it.
- Destructive commands now act on the engine's view in the venv, by design: `uv pip sync`,
  `--exact`, or `uv pip uninstall torch` remove the links (never the engine's files). On
  vllm, where the engine runs through `/venv/main`, that stops the engine until the user
  reinstalls. The runtime check names this state instead of leaving a bare ImportError.
- The image gains about 150k symlink inodes. The sync of a fresh mirror venv is small (tar
  stores links), but a venv that already holds real installs keeps its size.
- The first boot after rollout gives every volume a new `.environment_sync` directory
  (the hash changes), so a user's previous synced tree is left in place but no longer used.
- Installs into the system interpreter after the build (`uv pip install --system`,
  `apt install python3-...`) are invisible to `/venv/main`, and so to the engine on vllm and
  vllm-omni. The image READMEs now say to install into `/venv/main`.
- A conda upstream is not supported: conda can install Python packages without a
  `.dist-info`, which uv cannot see. Nothing checks for it statically.
- Shared libraries resolve `$ORIGIN` relative to the link, not its target. torch works
  because its `nvidia/*` libraries sit inside site-packages and the mirror reproduces that
  layout; an extension whose RPATH escapes site-packages would not. This is not checked
  statically: the engine import and the QA cell's live serve are where it would show.

## What would reverse this

- uv shipping discovery of inherited packages (the semantics of #11670) in a release we
  can use: `/venv/main` could go back to plain inheritance and the mirror would be deleted.
- A package on a supported image that writes into its own install directory at runtime
  (JIT caches under site-packages, for example), which would write through a link into the
  engine's tree. The feature-branch live serve is where this would show; it has not been
  observed.
- The live serve failing on the mirror in a way the prototype did not show.
